# DECISIONS — DSH-Studio-Runtime

> 只记录**无法仅靠阅读代码还原**的决策：选了什么、为什么、考虑过什么、限制在哪、还能不能改。
> 每条都标注依据。日期为决策发生的时间（本仓库自 2026-09-28 起有发布，决策多在 2026-09/10 形成）。

## D1 · Runtime 版本号 == Harness 版本号

- **选择**：`runtimeVersion` 就是官方 Harness 版本（`0.2.0-rc.1` 起），不引入任何构建计数后缀
  （`-verN`/`-rN`/`-rebuild-N`/`-revision-N` 全部被构建脚本与 publisher 显式拒绝）。
- **为什么**：用户可见的版本只应表达"这是哪个 Harness"；"哪个构建"是另一个维度，由 SHA-256 承担。
  早期确实用过 `-verN` 后缀，它把"构建批次"混进版本号，导致客户端排序、回滚、catalog 语义全部复杂化。
- **替代方案**：① 版本 + 构建计数（已废弃并清理）；② 完全独立的 Runtime 版本线（会与 Harness 失去对应关系）。
- **限制**：同版本只能有一个"当前"产物；重打包必须替换而非并行（见 D2）。
- **调整空间**：低。改动等于重定义客户端契约。

## D2 · 同版本重打包 = 例外恢复机制

- **选择**：允许对已发布版本重新打包，**替换**同一 release 的附件（tag/文件名/URL 不变），只更新 catalog
  里的 `sha256`；并把这件事在 `docs/repack-policy.md` 中限定为"白名单理由 + 必须记录原因"。
- **为什么**：依赖被 yank、构建基础设施缺陷、上游撤回版本——这些情况下"等下一个 Harness 版本"不可接受。
- **替代方案**：① 禁止重打包（会被迫发布假版本号）；② 允许同版本多构建并存（需要客户端支持多产物，破坏
  "每架构恰好一条 release"的契约）。
- **限制**：① 资产替换不是原子操作（逐文件上传 + CDN 传播），窗口内客户端会因 sha 不匹配而 fail closed；
  ② 客户端目前无法区分同版本不同字节（见 DEVELOPMENT_STATUS §4 第 7、8 条）。
- **调整空间**：**保留现有语义**。曾讨论用 `artifact.buildId` 表达构建身份，结论是：`artifact.sha256`
  已经是构建身份，缺的是**客户端持久化它**——那是客户端问题，不应为此扩 schema。

## D3 · 独立 Runtime 分发仓库（保留，而不是打进 App 或复用官方产物）

- **选择**：保留本仓库，走"签名 catalog + 客户端校验 + 原子安装 + 回滚"。范围收敛为构建/验证/签名/发布/发布后验证。
- **为什么**：① 官方**没有**可复用产物（npm 包不含 Node；桌面 Host 包 private 且从不发布；安装包是终端用户
  安装器、无再分发许可）；② Harness 每周多次发布，客户端不能跟着发版；③ 客户端是 Swift + WKWebView，
  用不了 Electron 的 Node。
- **替代方案**：① 打进 App（App 体积 +200MB/切片、更新被 App 发版绑死；只有上 Mac App Store 时才必需）；
  ② 复用官方桌面运行时（不存在，且 Host 是私有 Electron 组件）；③ 客户端直接 `npm install`（用户机器没有 Node）。
- **限制**：维护成本由我们承担（~5,965 行）；构建机完全可信。
- **调整空间**：架构成立；范围仍可继续收缩（插件市场解析、部分文档）。

## D4 · 签名与信任锚：单锚、编译进 App、fail closed

- **选择**：Ed25519 签名 catalog；公钥同时提交在 `keys/runtime-catalog-public.txt` 与客户端 Info.plist；
  keyID `runtime-catalog-v1`；签名脚本强制"派生公钥 == 已提交锚"。
- **为什么**：客户端必须能在"分发主机被攻破"的假设下拒绝伪造 catalog，因此锚不能远程获取。
- **替代方案**：① 远程取锚（等于没有信任根）；② KMS/HSM（此规模不划算）；③ 多锚/密钥列表（**未实施**，
  但已评估为"丢失/轮换时可减少一次危机"的改进方向）。
- **限制**：**任何换锚都必须发新版 App**；私钥丢失 = 更新链断（当前 P0）；轮换窗口期老 App 无法发现新 Runtime。
- **调整空间**：中。可为轮换能力在 App 侧引入"有序锚列表 + 显式激活索引"（需 App 配合）。

## D5 · 依赖闭包整体禁用 install scripts，新增脚本包必须显式登记

- **选择**：`--ignore-scripts` 安装整个依赖图；`Scripts/audit-dependencies.js` 让任何未登记的
  install/gypfile 包**直接失败**；白名单逐条写明"为什么不需要构建"。
- **为什么**：install script 是供应链攻击面；静默跳过会在用户第一次用到某个功能时才炸。
- **替代方案**：① 允许脚本执行（放弃这部分隔离）；② 只记录不失败（失去意义）。
- **限制**：白名单需要维护（目前 5 条）；上游改依赖时要跟着改。
- **调整空间**：低（这是刻意保留的信任边界）。

## D6 · Smoke 验证跑在**解包后的产物**上

- **选择**：`build-runtime.sh` 打包并算出 SHA-256 后，解包到临时目录，在**已发布的那些字节**上跑 smoke。
- **为什么**：权限位丢失、成员缺失、归档损坏只有打包后才可能出现。
- **替代方案**：直接在 staging 树上跑（会漏掉打包问题）。
- **限制**：不能覆盖"客户端机器上的实况"（如 Seatbelt 是否可用、真实 Intel 硬件）。
- **调整空间**：低。已确认这是本项目最有价值的验证环节。

## D7 · 数据兼容字段：现行方案已知不正确，替代方案待跨仓库实施

- **选择（现状）**：manifest/catalog 里 `dataFormat: { id: "sqlite-v2", compatibleWith: [], migration: null }`。
- **为什么（历史）**：该标签是客户端在"Harness 0.1.0-rc.8 的 sqlite schema 破坏性变更"后约定的契约代际名。
- **现状证据**：实际数据是 `$DSH_HOME/sessions/**/session.v4.jsonl.zstd`（无 `.db`），安装树内
  `session-format-catalog` 声明 `currentVersion: 4`，上游 SQLite provider 已被移除且旧 `.db` 既不读也不迁。
  因此该字段**既不描述事实、也从不触发隔离**。
- **替代方案（已设计未实施）**：构建期从产物自身派生 `dataFormat.id`（如 `session-v4`），`compatibleWith`
  取迁移链可读的旧代际；客户端改为"扫描 profile 实际代际"并据此拒绝跨代际回滚。见
  `docs/data-compatibility-contract.md`。
- **限制**：切换必须与 App 发版同步（旧 App 会把新 id 视为"未知"并 fail closed）。
- **调整空间**：方案已定，等 App 侧就绪；**禁止单方面改字段语义**。

## D8 · 插件市场 pin：保留字段，但解析职责待收敛

- **选择**：构建期解析 `dshmarket` 的兼容版本并写入 manifest/catalog（含 `integrity`、`harnessRange`）；
  客户端优先使用 Runtime 的 pin，回落到自带常量。
- **为什么**：客户端需要"经过验证的组合"而不必随市场变化发版。
- **代价（已知）**：`Scripts/resolve-plugin-market.js`（327 行）复刻了客户端范围语义，形成**两处 SemVer 语义**。
- **替代方案（未决）**：把解析交给客户端（它有官方那套 peer 预检 + 用户显式豁免）；Runtime 只保留"已测试组合"记录。
- **限制**：上游**没有**官方市场概念，`dshmarket` 是生态内第三方包。
- **调整空间**：中；需与 App 协商，且不应把复杂度简单搬过去。

## D9 · 上游没有桌面/运行时产物可复用（事实性决策依据）

- **结论**：不可复用。依据（只读检查官方仓库 `0.2.1-alpha.1`）：npm 包 `files` 只含 `lib/*.js`；
  `@deepseek-ai/dsh-desktop-host` 是 `private: true` 且注释写明"never published"；桌面 Host 以
  `ELECTRON_RUN_AS_NODE=1` 运行；唯一的"Node + Harness"单文件产物是 Python SDK 的 wheel（无插件面）。
- **影响**：决定了 D3。

## D10 · 客户端与发布端的**顺序类**不变量（历史包袱）

- **选择**：catalog 只描述**一个当前版本**（每架构一条 release）；版本比较用 SemVer + prerelease 规则
  （`rc.9 < rc.10 < 0.2.0 < 0.2.1`），绝不字符串比较；发布端拒绝 catalog 降级。
- **为什么**：客户端要能"只读一个文件就决定装什么"，且历史事故（`-verN` 时代的错序）证明字符串比较不可用。
- **限制**：客户端无法从 catalog 得到历史版本的 sha → **回滚不能依赖下载**，只能依赖本地保留的目录。
- **调整空间**：低。

## D11 · 作者身份与提交约定

- **选择**：所有提交只署 `SteveTanSaMa`；**不添加任何 bot / AI 署名**（无 `Co-authored-by` 之类）。
- **为什么**：仓库所有者明确要求"只能用我的名字"。
- **限制**：CI 自动创建的 release 仍会显示为 `github-actions[bot]`（未引入 PAT），属已知偏差。
- **调整空间**：低（除非引入 PAT，而那会带来新的凭据管理成本）。

## D12 · 文档语言策略

- **选择**：`README.md`（中文，权威）+ `README.en.md`（英文镜像）；`docs/**` 只有中文。
- **代价（已知）**：两份 README 需人工同步，是持续维护成本。
- **调整空间**：中；可把英文 README 收敛为摘要 + 链接（尚未决定）。
